# Rebuild VizCraft around models, packs and generators

*Research date: 2026-10-17. This report is the research behind the cascade plan in [ROADMAP.md](../../ROADMAP.md) (Cascades 2 to 8) and the planned model architecture in [docs/architecture.md](../architecture.md#planned-not-yet-built). It is kept as written: recommendations marked "(synthesis)" are the report's own design proposals rather than sourced findings, and every other claim carries its source link.*

VizCraft should stop growing as a shape drawer and become a **local, model-backed engineering workbench**. In that workbench every shape is a view of a typed semantic element. Notations ship as data packs that drive the palette, the connection rules, validation and agent discovery. Each pack ends in an export ladder that runs from CSV lists, through open interchange formats, to code scaffolds regenerated under a contract that never destroys hand-written code. The professional tools people pay for in all three target audiences sell the database behind the drawing, not the drawing. EPLAN numbers and cross-references devices automatically. AVEVA and Autodesk AutoCAD P&ID run consistency checks with severities. Sparx Systems Enterprise Architect (EA) and Dassault Systemes Cameo put a model tree, not a shape grid, in the main pane. itemis CREATE and Quantum Leaps QM turn statecharts into C, C++, Rust-adjacent and SCXML output. VizCraft's existing architecture is unusually well suited to this: every action is a command with an id, callers can choose stable element ids, and an MCP server already exists. The research found that agent integrations from JGraph's draw.io, Lucid Software and tldraw centre on generating whole diagrams. Validated, reversible, fine-grained editing of an existing model is the opening. The concrete recommendation follows from that. Keep the slimmed remainder of Cascade 2 and the Cascade 3 wiring now being planned. Then insert a **model core cascade** (semantic model, notation-pack format, rules engine, model tree, inspector, Problems pane, scoped palette) **before any domain stencils**. Then a **pattern and generator framework**. Then three audience packs built in parallel: industrial (P&ID with ISA-5.1 tags, cause-and-effect matrices, SFC, Structured Text, Purdue and IEC 62443 zones), embedded (statecharts, register and memory maps, packet layouts, WaveJSON) and enterprise (C4, ER, UML, BPMN, ArchiMate 4). Recommendations marked **(synthesis)** are this report's own design proposals rather than sourced findings.

## The open niche is a fast local modeller with generators, not a bigger shape library

Three classes of incumbent each leave a gap VizCraft can occupy. Heavy repository tools such as Sparx EA and Cameo have real models. Sparx calls its Project Browser tree "the primary mechanism" for browsing a model ([Sparx EA user guide](https://www.sparxsystems.com/enterprise_architect_user_guide/14.0/model_navigation/projectexplorer.html)). But reviewers rate Cameo harder than other products for team collaboration, on a thin sample ([GetApp](https://www.getapp.ca/software/2052448/cameo-enterprise-architecture)), and Capella users must write Java/EMF plugins to customise validation ([Capella forum](https://forum.mbse-capella.org/t/verify-architecture-design-with-some-kind-of-animation/7157)). Developer tools are model-backed but single-notation. IcePanel's model is "view-agnostic", so an object edited once updates every diagram that shows it, but it is C4 only and SaaS ([IcePanel docs](https://docs.icepanel.io/core-features/modelling)). Structurizr loses manual layout when DSL elements are renamed or reordered, because layout is matched by generated ids ([Structurizr docs](https://docs.structurizr.com/ui/diagrams/manual-layout)). General drawing tools have polish but no model. Microsoft Visio reviewers complain that it "can create connections where it is not wanted" ([PeerSpot](https://origin.peerspot.com/products/visio-reviews/page-3)). A network engineer called Visio "tedious and rigid", because moving one device forces links to be redrawn ([AusNOG](https://lists.ausnog.net/pipermail/ausnog/2022-October/046085.html)). Lucid's VSDX export does not keep connector glue ([Lucid community](https://community.lucid.co/product-questions-3/exports-to-vsdx-and-vds-not-preserving-connection-points-10287)).

Competing on shape count is futile. The draw.io MCP alone indexes **more than 10,000 shapes** for agents to search ([jgraph/drawio-mcp](https://cdn.jsdelivr.net/gh/jgraph/drawio-mcp@main/README.md)), and a clean-room project cannot copy vendor stencils. Industrial tools show what the paid features actually are. EPLAN Electric P8 sells automatic wire connection, numbering, cross-referencing and generated terminal, wire and BOM reports ([EPLAN](https://eplan.com/us-en/products/eplan-electric-p8.html); [GetApp](https://www.getapp.com.au/compare/177903/2058288/electric-p8/vs/autocad-electrical)). AVEVA Diagrams runs consistency checks graded Error, Warning and Info, and since May 2023 keeps its built-in rules in an open format customers can edit ([AVEVA docs](https://docs.aveva.com/bundle/diagrams/page/1052663.html); [AVEVA brochure](https://www.aveva.cn/content/dam/aveva/documents/brochures/Brochure_AVEVA_Diagrams_23-11.pdf.coredownload.inline.pdf)). Siemens markets "generating instead of programming": external programs drive the Siemens TIA Portal Openness API to create PLC objects ([Siemens webinar](https://assets.new.siemens.com/siemens/assets/api/uuid:dd6de7e9-f460-4281-b2b0-450d2bbddd02/siemens-australia-options-sivarc-prodiag-energy-suite-webinar-16.pdf)). That is exactly the relationship VizCraft's command layer and MCP server create between an agent and the editor.

The AI landscape sharpens the opening. Lucid shipped an in-app AI panel in October 2025 and an MCP server in November 2025 ([Lucid community](https://community.lucid.co/community-news-and-announcements-9/welcome-to-the-future-of-work-with-lucid-ai-in-lucidchart-11767)). tldraw ships an agent starter kit that creates, updates and deletes shapes ([tldraw](https://tldraw.dev/starter-kits/overview)). The official draw.io MCP generates XML or Mermaid diagrams, and its README does not document reading, modifying and writing back an existing diagram ([jgraph/drawio-mcp](https://cdn.jsdelivr.net/gh/jgraph/drawio-mcp@main/README.md)). **(synthesis)** VizCraft should therefore make agents first-class model editors, not diagram generators. That means four capabilities. Agents can discover the notation schema. They issue fine-grained commands against stable ids. They receive structured validation issues after every command, so they can repair their own mistakes. They tidy layout with commands that never disturb a human's arrangement. The steelman for staying generic is that broad drawing tools have far larger audiences. But that market already has free incumbents, and the owner has ruled out the toy-drawer positioning. The defensible ground is depth in three audiences that share one engine.

## Replace the shape grid with a model tree, a scoped palette and on-canvas insertion

Professional modelling tools converge on one workspace shape. A model tree dominates the left pane. A typed inspector sits on the right. A small creation palette is scoped to the active diagram type, and most insertion happens on the canvas. Sparx EA documents a Diagram Toolbox with one subsection per diagram type, alongside the Quick Linker and on-canvas context menus ([Sparx Building Models](https://sparxsystems.com/resources/user-guides/16.0/modeling/building-models.pdf)). Cameo's Containment tree is where users reach, create and open every element. Its Specification windows have Standard, Expert and All modes that hide or reveal properties ([No Magic docs](https://docs.nomagic.com/SYSML2P/2026x/working-with-containment-tree-254422403.html)). In Eclipse GLSP and Sirius the palette is generated from the language definition, not hardcoded ([EclipseSource](https://eclipsesource.com/blogs/2019/11/04/introducing-the-graphical-language-server-protocol-platform-eclipse-glsp/); [Sirius docs](https://eclipse.dev/sirius/doc/0.9/specifier/diagrams/Diagrams.html)). GLSP validation markers appear on elements and in a Problems view that jumps to the offending element ([GLSP validation](https://eclipse.dev/glsp/documentation/validation/)).

Fast insertion in the best editors bypasses palettes entirely. Visio AutoConnect shows directional arrows on hover; hovering an arrow opens a mini toolbar of the first four Quick Shapes, and clicking one adds it already connected ([Microsoft Support](https://support.microsoft.com/en-US/Visio/add-connectors-between-visio-shapes)). In draw.io, double-clicking empty canvas opens a shape picker, hover arrows clone and connect, and Alt+Shift+Arrow does the same from the keyboard ([draw.io docs](https://www.drawio.com/docs/tutorials/draw-faster-diagrams/)). Figma's Cmd/Ctrl+K menu searches commands, plugins and library components, though users complain it does not search layers ([Figma Help](https://help.figma.com/hc/en-us/articles/23570416033943-Use-quick-actions); [Figma forum](https://forum.figma.com/t/global-search-similar-to-sketch-runner-or-apple-spotlight/549)). Visio's limit is visible: suggestions come from stencil order, not from what is legal next. **(synthesis)** VizCraft can do better by suggesting only element and relationship types the active notation pack allows from the hovered element. This is how EA's Quick Linker is widely understood to work, though the research could not fetch Sparx's page to confirm it.

**(synthesis)** The recommended workspace, built from these precedents:

| Region | Contents | Replaces or extends |
|---|---|---|
| Left dock, tab 1: Model | Containment tree. Project, then packages or plant areas, then elements grouped by type, each showing its views. A Diagrams/Sheets branch. A Context mode that follows the canvas selection. "Show in all views" and "delete from view vs delete from model" actions | New; becomes the default left tab |
| Left dock, tab 2: Palette | Compact, searchable palette filtered to the active view's notation and viewpoint, grouped by the pack's palette groups. Free drawing primitives collapse into one "Drawing" group at the bottom | Replaces today's full-height Basic and Flowchart tile grid |
| Left dock, tab 3: Patterns | Parameterised pattern library filtered by audience and notation, each entry opening a parameter form | New |

Lucid put its AI chat panel at the top of the left panel ([Lucid community](https://community.lucid.co/community-news-and-announcements-9/welcome-to-the-future-of-work-with-lucid-ai-in-lucidchart-11767)). **(synthesis)** VizCraft is better served by an agent activity view in the bottom dock that lists each agent command batch as one undoable transaction. A human can then review and revert, which keeps the left dock for the model.

## Make shapes views of semantic elements defined by notation packs as data

Every serious repository tool separates a model of elements and relationships with identity from views that reference them. Sirius is the clearest declarative precedent. A Viewpoint groups representations (diagrams, tables, matrices, trees) over a domain model. Its diagram specification declares layers, node, container, port and edge mappings, conditional styles, tools, filters and validation rules, all in one specification file ([Sirius viewpoints](https://eclipse.dev/sirius/doc/specifier/general/Specifying_Viewpoints.html); [Sirius features](https://eclipse.dev/sirius/features.html)). Sirius rules carry a level (Information, Warning, Error) and an audit expression ([Obeo](https://news.obeosoft.com/post/fix-it-sirius)). GLSP 2 supports live validation after every model update plus on-demand batch validation for expensive checks ([GLSP validation](https://eclipse.dev/glsp/documentation/validation/); [EclipseSource GLSP 2](https://eclipsesource.com/blogs/2024/01/31/eclipse-glsp-2-elevating-web-based-diagram-editors/)). Structurizr adds two ideas worth taking. `!impliedRelationships` derives parent-level links from child links, and `archetypes` define custom element types with default properties ([Structurizr DSL](https://docs.structurizr.com/dsl/language)). SysML v2, adopted by OMG in July 2025, puts textual and graphical notation of one model on equal footing behind a standard query-and-update API ([OMG](https://www.omg.org/news/releases/pr2025/07-21-25.htm); [itemis](https://www.itemis.com/en/glossary/sysml-v2/)). This mirrors VizCraft's "every action is a command" design.

**(synthesis)** The model architecture VizCraft should adopt has five parts.

**Semantic model.** A new `vizcraft-model` crate in the model layer holds `Element`, `Relationship` and a containment tree. An `Element` has a stable id, a pack-qualified type such as `pid.CentrifugalPump` or `c4.Container`, typed properties, tags and an owner. A `Relationship` has an id, a type, source and target element ids (optionally ports) and properties. A `View` holds a viewpoint and layout. Today's `Shape` gains an optional `element` reference and `Connector` an optional `relationship` reference. Shapes without one stay valid as free drawing, so Cascade 1 documents keep working. Geometry lives in the view keyed by element id, never in the model. This is the direct fix for Structurizr's layout loss.

**Notation packs as data.** A `vizcraft-notation` crate defines a versioned pack schema, loaded from JSON or TOML. Each pack declares:

- element types with property schemas (type, unit, enum, required, default) and ports
- original glyph definitions drawn from public specification descriptions
- a connection table of source type, relationship type and target type, with multiplicity
- conditional styles keyed on property values
- palette groups and viewpoints (named filters of allowed types)
- identifier formats, such as an ISA-5.1 tag composed as letters plus loop number plus suffix
- validation rules with severity
- the templates, patterns and exporters the pack supports

One file then drives the palette, hover suggestions, the magic connector, the validator, the Inspector and MCP schema discovery. Basic and Flowchart should be re-expressed as the first two packs, to prove the format before any domain work.

**Rules engine.** Cheap rules run live after each command; expensive rules run in batch on selection, sheet or project. Examples of cheap rules are an illegal relationship, a missing required property or a duplicate tag. Examples of expensive ones are statechart reachability and cross-sheet continuity. Issues are structured records of rule id, severity, element ids and a message, and are returned in the result of every MCP command batch. AVEVA's editable open-format rules show that customers want rules as data ([AVEVA](https://docs.aveva.com/bundle/diagrams/page/1052663.html)). Capella's Java-only extension shows the cost of not doing so.

**Identity services.** A project-wide registry handles tags and reference designations: auto-numbering, uniqueness, and composed identifiers. AutoCAD P&ID line tags are composed from size, spec, service and number subparts. A mismatched format makes every pipe show as unmatched ([Autodesk AU class](https://static.au-uw2-stg.autodesk.com/Class_Presentation_ENR323574_Quentin_Contreras.pdf)). IEC 81346 reference designations use letter-coded object classes (Q for circuit breaker, T for transformer) and a "-" product-aspect prefix ([myElectrical](https://myelectrical.com/notes/entryid/24/iec-reference-designations); [81346.com](https://www.81346.com/81346-2)). Off-page connectors become paired objects. EPLAN matches interruption points by device tag in star or chain layouts and inserts cross-references live ([EPLAN Help](https://www.eplan.help/en-us/Infoportal/Content/Plattform/2026/Content/htm/xessettingsgui_k_querverweisarten.htm)). AutoCAD P&ID flags off-page connectors that have no continuation ([Autodesk help](https://help.autodesk.com/cloudhelp/2017/ENU/Plant3D-UserGuide/files/GUID-3FDD798F-FB2A-432C-804E-7A616ABFB79A.htm)).

**Derived views.** Tables and matrices are first-class views over the model, editable in place: instrument index, I/O list, line list, cause-and-effect matrix, relationship matrix, RACI. So are generated diagrams: impact analysis, implied-relationship roll-ups and drill-down child views. Visio's data linking matches external rows to shapes by key, and its Data Visualizer syncs both ways with Microsoft Excel ([Microsoft Support](https://support.microsoft.com/lt-LT/Visio/tips-and-tricks-for-linking-data); [Data Visualizer](https://support.microsoft.com/en-us/Visio/create-a-data-visualizer-diagram)). Those are the reference behaviours for table round trips.

Layout must split into three commands, because agents and humans share documents. ELK Layered exposes more than 140 options, including interactive mode, layer constraints and model-order preservation ([GD 2024](https://drops.dagstuhl.de/storage/00lipics/lipics-vol320-gd2024/LIPIcs.GD.2024.56/LIPIcs.GD.2024.56.pdf); [ELK blog](https://eclipse.dev/elk/blog/posts/2023/23-01-09-constraining-the-model.html)). yFiles' incremental from-sketch layout rearranges only changed parts to preserve the user's mental map ([yFiles docs](https://docs.yworks.com/yfiles-html/dguide/layout-incremental_layout/)). The draw.io MCP keeps an ELK relayout and a libavoid route-only pass as mutually exclusive options ([jgraph/drawio-mcp](https://cdn.jsdelivr.net/gh/jgraph/drawio-mcp@main/README.md)). **(synthesis)** VizCraft should expose three commands, all built on the existing `vizcraft-layout` and `vizcraft-routing` crates:

- `layout.full`, which rearranges everything
- `layout.incremental`, which pins existing nodes and places new ones
- `layout.route`, which reroutes connectors and never moves a node

## Twelve notation packs across three audiences, each with an export ladder

**(synthesis)** Each audience needs a few deep packs rather than many shallow stencils. Every pack climbs the same ladder:

1. Tables and documentation (CSV, XLSX, Markdown)
2. Open interchange formats
3. Code scaffolds
4. Later, reverse-engineering imports

The domain notes below establish what each pack must model; the tables give the recommended contents and exports.

### Industrial automation: identity, cross-references and IEC 61131-3 output

Automation drawings are linked, data-bearing documents whose semantic core is identity. ANSI/ISA-5.1-2024 renamed itself "Instrumentation and Control Symbols and Identification" ([ISA](https://www.isa.org/news-press-releases/2024/october/widely-used-engineering-symbols-and-drawings-stand)). Its tags combine one to four function letters, a loop number and optional prefix and suffix; this structure is documented in a secondary source ([Industrial Monitor Direct](https://industrialmonitordirect.com/tr/blogs/knowledgebase/plc-and-dcs-tag-naming-conventions-isa-51-structure-and-examples)). ISA-5.4 sets the minimum content of loop diagrams: components, interconnections, energy sources and control actions ([ISA](https://www.isa.org/standards-and-publications/isa-standards/isa-standards-committees/isa5-4)). CERN built a cause-and-effect-matrix method covering the IEC 61511 lifecycle from specification to generated PLC code ([CERN ICALEPCS 2019](https://epaper.kek.jp/icalepcs2019/papers/mopha041.pdf)). IEC 61131-3 edition 4 (May 2025) removed Instruction List and added UTF-8 strings ([IEC webstore](https://webstore.iec.ch/en/publication/68533)), so generators should target Structured Text and never IL. IEC 62443 zones and conduits must be risk-defined. NIST SP 800-82r3 moved away from presenting Purdue as the reference architecture ([Trout Software](https://www.trout.software/resources/iec-62443)), so the Purdue template is a starting draft, not a zone map. The DEXPI class model gives a ready, interoperable vocabulary for an internal P&ID schema. It includes Equipment subtypes, PipingNetworkSegment, ProcessInstrumentationFunction and SignalConveyingFunction ([OPC 30250](https://reference.opcfoundation.org/specs/OPC-30250/7)).

| Pack | Model content | Tier 1 export | Tier 2/3 export |
|---|---|---|---|
| P&ID / PFD | DEXPI-named equipment, nozzles, piping segments, inline valves, instrumentation functions, signal lines; composed line numbers and ISA-5.1 tags; paired off-page connectors | Line, equipment, instrument and valve lists (CSV/XLSX) | DEXPI Proteus XML (tier 2); DEXPI 2.0 once final |
| Instrumentation and loops | Loops as model objects; loop diagrams as generated views per loop with location sections; I/O points (signal type, range, rack/slot/channel) | Instrument index, I/O list, ISA-18.2-shaped alarm list | OPC UA NodeSet2 of the tag hierarchy |
| Safety and logic | Cause-and-effect matrix view linked to tags; interlock and permissive logic trees; SFC steps and transitions | ST Boolean interlocks per CEM row; ST CASE state machines from SFC | PLCopen XML (IEC 61131-10) POUs and SFC |
| Control modules | Motor and valve modules with states, feedbacks, interlocks, hand/off/auto | ST function block skeletons, global variable list from I/O list | PLCopen XML |
| OT architecture | Purdue bands, IEC 62443 zones (SL-T) and conduits, assets | Zone/conduit and asset inventory CSV | AutomationML CAEX hierarchy |
| ISA-88/95 hierarchy | Physical model (cell, unit, equipment module, control module) and procedural model (procedure to phase), edited as an outline with generated tree layout | Equipment hierarchy CSV | B2MML/BatchML; MTP later |
| Electrical (second wave) | IEC 81346 three-aspect designations, contacts and coils with cross-reference images, terminals, wires, potentials | Terminal, wire and cable lists, BOM | — |

The tier ordering follows formats' maturity. PLCopen XML is formalised as IEC 61131-10 with an XSD and can carry graphical layout, though importing tools need not support every feature ([IEC](https://webstore.iec.ch/publication/33034); [Control Engineering](https://www.controleng.com/understand-iec-61131-10-to-more-easily-transfer-plc-applications/)). AutomationML wraps CAEX, COLLADA and PLCopen XML ([OPC 30040](https://reference.opcfoundation.org/specs/OPC-30040/4.1)). DEXPI 2.0's status conflicts across sources: one snippet claims release in late 2025, while a March 2026 article still calls it forthcoming ([Wiley](https://processtechnology.wiley.com/de/Forschung/dexpi-2-0-synergistic-integration-of-pfd-and-pid-in-a-unified-digital-model)). The new format should wait. MTP remains a VDI/VDE/NAMUR 2658 guideline with only an IEC 63280 work-item proposal ([PNO roadmap](https://se.profibus.com/fileadmin/user_upload/MTP_Status_Roadmap_2024-06-11.pdf)). B2MML now includes a JSON Schema of ISA-88/95 ([Control Engineering](https://www.controleng.com/?p=79782)). An existing node-opcua modeler already exposes YAML-to-NodeSet2 as an MCP server ([socket.dev](https://socket.dev/npm/package/node-opcua-modeler-mcp-server)), which confirms the agent-plus-standard-format pattern. Substation single-line diagrams exporting IEC 61850 SSD files ([Wikipedia: SCL](https://en.wikipedia.org/wiki/Substation_Configuration_Language)) are a niche to defer.

### Embedded and systems software: round-trip open formats instead of inventing new ones

Register, timing and state-machine work already has mature open formats and generators, so VizCraft should be a visual editor over them. SystemRDL 2.0, IP-XACT IEEE 1685-2022 and CMSIS-SVD describe registers ([PeakRDL](https://peakrdl.readthedocs.io/en/latest/systemrdl-tutorial.html); [DVCon tutorial](https://dvcon-proceedings.org/wp-content/uploads/Tutorial-IP-XACT-IEEE1685-from101-to-latest-info.pdf)). svd2rust turns SVD into a type-safe Rust peripheral crate ([docs.rs](https://docs.rs/svd2rust/0.14.0)), and the `svd-parser` crate already models SVD in Rust ([docs.rs](https://docs.rs/svd-parser/^0.5.0)). Exporting SVD is therefore higher leverage than writing a PAC generator. SCXML is the only W3C-standard statechart interchange format and ships a conformance test corpus ([W3C](https://w3.org/TR/scxml/); [implementation report](https://www.w3.org/Voice/2013/scxml-irp/)). itemis CREATE shows the expected bundle:

- a textual generator model
- generated code in `src-gen` beside hand-written `src`
- SCXML export
- live checks for unreachable states, dead ends and unknown events
- a simulator that highlights active states

([itemis](https://www.itemis.com/en/yakindu/state-machine/documentation/user-guide/setting_up_a_code_generator_project); [Eclipse Marketplace](https://marketplace.Eclipse.org/content/yakindu-statechart-tools); [itemis simulation](https://www.itemis.com/en/products/itemis-create/documentation/user-guide/simulating_statecharts_web)). For Rust targets, `statig` supports hierarchical no_std machines ([docs.rs](https://docs.rs/statig)), while `smlang` is a flat Boost-SML-style DSL ([docs.rs](https://docs.rs/crate/smlang/latest)). A generator must therefore reject or flatten constructs a target lacks. WaveJSON is the de facto timing and bitfield text format ([WaveJSON wiki](https://github.com/drom/wavedrom/wiki/WaveJSON)). `cantools generate_c_source` turns a DBC into C pack and unpack code ([cantools](https://cantools.readthedocs.io/)). No maintained visual-graph-to-ROS 2-package generator was found: rqt_graph only visualises, and ROSgen is inactive ([ROS docs](https://docs.ros.org/en/kilted/p/rqt_graph/rqt_graph.dotcode.html); [ROSgen](https://github.com/FBarrca/ROSgen)).

| Pack | Model content | Imports | Exports and scaffolds |
|---|---|---|---|
| Statechart | Composite and orthogonal states, history, guards, entry/do/exit, events with payloads | SCXML | SCXML; C switch style (MISRA-friendly) or table style; Rust `statig` (hierarchical) or `smlang` (flat); QP-style C handlers; transition-coverage test sequences |
| Register map | addrmap, register file, register, field (access, reset, side effects), enums | SVD (via `svd-parser`), SystemRDL, IP-XACT | C header (offsets, masks, optional struct overlay), SVD (feeds svd2rust), WaveDrom bitfield JSON, Markdown register tables |
| Memory map | Address-ordered regions (flash, RAM, bootloader, A/B slots) | GNU ld map (later) | GNU ld `MEMORY {}` block, C region constants; overlap, alignment and overflow validation |
| Packet and frame | Field rows on a 32-bit grid (offset, width, endianness, type) reusing the bitfield model | — | C packed struct and macros, Rust (de)serialiser, RFC-style ASCII, test vectors |
| Timing | Signal lanes, edges, markers | WaveJSON | WaveJSON, SVG |
| Component and port architecture | Typed provided/required ports using AUTOSAR's taxonomy (sender-receiver, client-server, mode, parameter); buses as typed connectors | Graphviz DOT (Doxygen, cargo-depgraph) | Interface headers, port compatibility validation |
| RTOS and ROS 2 graphs | Tasks (priority, stack, period), ISRs, queues; ROS 2 nodes, topics, services, actions | DOT from rqt_graph | Task tables (FreeRTOS, Zephyr, RTIC lines); ROS 2 package skeleton with launch file |
| CAN and protocol sequences | Messages and signals; MSC/UML sequence with fragments | DBC (later) | DBC text (then cantools); per-lifeline protocol state-machine skeletons |

The AUTOSAR port kinds come from public ARXML tooling documentation ([MathWorks](https://www.mathworks.com/help/autosar/ug/autosar-code-gen-files.html); [autosar package](https://autosar.readthedocs.io/en/stable/autosar4_guide/ports.html)). Call graphs from cargo-callgraph become unreadable beyond about 500 lines of source ([cargo-callgraph](https://github.com/robinmoussu/cargo-callgraph)). Any DOT import therefore needs collapse and filter commands from day one.

### Enterprise and software architecture: target ArchiMate 4, lead with C4 and ER

ArchiMate 4 replaced 3.2 in April 2026 ([Open Group](https://www.opengroup.org/The-Open-Group-Announces-ArchiMate%C2%AE-4-Specification)). Vendor summaries report a 30 percent cut from 60 to 42 concepts, layers renamed to domains, merged behaviour concepts and relationship multiplicity ([Alfabet/Bizzdesign](https://alfabet.com/blog/archimate-4-changes)). The specification text is licence-gated, and vendors disagree on whether Composition survived. That pack should come after the specification is read, with 3.2 import kept for the installed base. C4 defines four core and three supplementary diagrams and is deliberately notation-independent ([c4model.com](https://c4model.com/)). Structurizr DSL is its model-as-code reference. Camunda documents the BPMN element coverage a modeller must offer ([Camunda](https://docs.camunda.io/docs/components/modeler/bpmn/bpmn-coverage/)). OWASP Threat Dragon auto-generates threats from DFD elements ([OWASP](https://owasp.org/www-project-threat-dragon/)). Context Mapper names the DDD relationship patterns and generates service contracts, but looks lightly maintained ([Context Mapper](https://contextmapper.org/docs/home/)). Mermaid now lists 31 diagram types ([Mermaid](https://mermaid.js.org/intro/)). Atlas shows the ER-to-migration path: it diffs a desired schema against a live one and emits migration SQL ([Atlas](https://atlasgo.io/guides/evaluation/schema-as-code)).

| Pack | Model content | Imports | Exports and scaffolds |
|---|---|---|---|
| C4 | Person, system, container, component, deployment nodes; implied relationships; drill-down | Structurizr DSL, Mermaid C4 | Structurizr DSL, Mermaid, PlantUML; Docker Compose and Kubernetes manifests from deployment views |
| ER / data | Conceptual, logical and physical levels; crow's foot cardinality | SQL DDL (first reverse-engineering target) | SQL DDL per dialect, DBML, migration diff between model versions, ORM entities (Diesel, SeaORM, SQLAlchemy, JPA) |

| BPMN 2.0 | Pools, lanes, tasks, events, gateways, subprocesses | BPMN XML | BPMN XML with DI and stable ids; engine extensions as an optional profile; DMN later |
| API and events | Services with interfaces, channels, messages linked to ER/class types | OpenAPI 3.x, AsyncAPI 3 | OpenAPI 3.1, AsyncAPI 3.0, protobuf with gRPC services, event JSON Schema |

Team Topologies' four team types and three interaction modes ([Team Topologies](https://teamtopologies.com/key-concepts)) are compact enough to be a pack. So are the DDD Crew context-map patterns ([ddd-crew](https://github.com/ddd-crew/context-mapping)). **(synthesis)** Generic flowchart, swimlane, mind map, org chart and network diagrams become a "General" pack. Network shapes are drawn originally, and vendor cloud icon sets stay out under the clean-room rule. The pack remains available but is no longer the identity of the app.

## Generate scaffolds under a contract that never destroys hand-written code

Code generation earns trust only when regeneration is safe, and the established mechanisms have known failure modes. Protected regions reinsert hand-written content by identification string. If identifiers change or collide, that content can be lost ([Greifenberg et al.](https://arxiv.org/pdf/1509.04498)). The generation gap pattern keeps generated and hand-written code in separate classes, so generated files are never edited. This is safer but doubles the class count ([Fowler](https://www.martinfowler.com/dslCatalog/generationGap.html)). STMicroelectronics' STM32CubeMX preserves code only inside named `USER CODE BEGIN/END` markers and deletes everything else on regeneration ([TouchGFX docs](https://support.touchgfx.com/docs/development/board-bring-up/how-to/01-create-project)). itemis separates `src-gen` from `src` ([itemis](https://www.itemis.com/en/products/itemis-create/documentation/tutorials/tutorial_generating-statechart-code)). MathWorks Stateflow writes transition traceability comments into generated code ([MathWorks](https://www.mathworks.com/help/ecoder/ug/enhancing-readability-of-generated-code-for-flow-graphs.html)). QM's faster QMsm output is practical only to regenerate, never to hand-maintain ([QM](https://www.state-machine.com/qm/sm.html)). EventCatalog regenerates from AsyncAPI while preserving user markdown ([EventCatalog](https://eventcatalog.dev/docs/plugins/asyncapi/intro)), which is the documentation version of the same contract.

**(synthesis)** A new `vizcraft-codegen` crate in the model layer, with no UI dependencies, should host a generator framework with this contract:

| Contract clause | Mechanism |
|---|---|
| Generation is a command | `generate.preview`, `generate.run`, `generate.check`; reachable from the Generate ribbon tab, the CLI (`vizcraft-cli generate --check` for CI) and MCP, so an agent can generate, build, test and iterate |
| Configuration is a file in the repo | A generator spec (target, options, output directory, model scope), analogous to itemis `.sgen`, so the choice of output style is versioned |
| Ownership is explicit | A manifest beside the output lists every generated file with the checksum last written; VizCraft writes only files it owns, only inside the declared directory |
| Separation by default | Generation gap per language. Rust: generated module plus a user-implemented trait for actions and guards. C: generated `.c` calling `extern` prototypes the user implements. Languages with partial classes use them |
| Protected regions only when unavoidable | Single-file targets (for example a PLC POU) use regions keyed by element id, never by position or name |
| Traceability | Every generated construct carries `vizcraft:id=<element id>` in a comment or annotation; renames go through a rename map so identifiers do not churn silently |
| Determinism | Stable ordering and formatting; regenerating an unchanged model is byte-identical |
| No silent overwrite | Preview shows a diff in the bottom dock. If an owned file's checksum differs from the manifest, the generator three-way merges (last generated, on disk, new) or stops with an issue |
| Honest targets | Each target declares a construct-support matrix (for example `smlang` has no hierarchy); unsupported constructs raise validation errors or are flattened only when the user opts in |
| Prefer standard intermediates | Emit SVD for svd2rust, DBC for cantools, OpenAPI/AsyncAPI/protobuf for existing stub generators, and PLCopen XML for PLC IDEs, rather than writing runtimes |
| Verify fidelity | Where an importer exists (DDL, SCXML, SVD, OpenAPI), re-import generated output in tests and compare with the model |

Re-import of text formats follows the same principle in reverse. Imported elements keep a model id. Re-import then updates the model, keeps view geometry for existing ids, auto-places new elements with `layout.incremental` and flags removed ones. This is the local equivalent of IcePanel's drift notifications and Brainboard's scheduled drift scans ([IcePanel](https://docs.icepanel.io/features); [Brainboard](https://brainboard.co/pricing)).

## Ship patterns as parameterised generators over about twelve layout primitives

Every target audience has a stable, citable pattern vocabulary:

- **Workflow:** the Workflow Patterns initiative grew from about 20 control-flow patterns to 43 in its 2006 revision ([TU Wien](https://wfm.ec.tuwien.ac.at/node/46)).
- **Integration:** Enterprise Integration Patterns names routing, channel, transformation and endpoint patterns ([EIP](https://www.enterpriseintegrationpatterns.com/patterns/messaging/toc.html)).
- **Cloud:** Microsoft Azure's catalogue lists 44 cloud patterns and documents compositions such as Retry plus Circuit Breaker, and Saga built on Compensating Transaction ([Azure](https://learn.microsoft.com/en-us/azure/architecture/patterns/)).
- **Microservices:** microservices.io covers decomposition, data management and transactional-messaging patterns ([microservices.io](https://microservices.io/patterns/index.html)).
- **Process control:** Skogestad treats cascade, ratio, feedforward, decoupling, selectors, split range and the Smith predictor as standard advanced-regulatory-control elements ([Skogestad](https://folk.ntnu.no/skoge/publications/2023/skogestad-advanced-regulatory-control_arc/other-old/Advanced_regulatory_control-Annual_reviews_in_Control%20(41).pdf)).
- **Safety:** Douglass catalogues Watchdog, Triple Modular Redundancy, Monitor-Actuator and Safety Executive ([O'Reilly](https://www.oreilly.com/library/view/real-time-design-patterns/0201699567/ch09.html)).

Existing tools package patterns as static templates, as data-driven generation such as Visio's Data Visualizer, or as text macros such as the PlantUML C4 library ([PlantUML stdlib](https://plantuml.com/stdlib)). The research found no tool offering argument-driven pattern insertion, such as a five-step saga, as a first-class editor command.

**(synthesis)** A `vizcraft-patterns` crate defines each pattern as a generator with typed parameters: counts, labels, mode enums, tag prefixes or a data table. It emits model elements and relationships, not bare shapes, so they appear in the model tree and other views. It then applies a layout primitive and commits as one undoable compound command. The inserted group records the pattern id and parameter values, so `pattern.reparameterize` can change a saga from four steps to six while keeping manual label edits. Every pattern is listed in the Patterns tab, the Cmd/Ctrl+K palette and one `pattern.insert(name, args)` command with a discoverable schema. Catalogue names (WCP, EIP, Azure, ISA-88, Team Topologies) then double as a vocabulary agents already know. Where a pack has a generator, the pattern links to it. A cascade-loop pattern exports its ST skeleton; a CQRS pattern exports event schemas and handler stubs.

The catalogue collapses onto about twelve layout primitives. `vizcraft-layout` already provides layered, tree, radial and force. The others are new, mostly constrained variants of layered layout plus a grid and nested-container packer:

- pipeline with a parallel band
- two-row forward and compensation chain
- hub and spoke
- horizontal bands or swimlanes
- matrix
- nested containers
- concentric rings
- timeline
- N-channel voter

| Pattern (parameters) | Audience and pack | Layout primitive | Linked scaffold |
|---|---|---|---|
| Single PID loop (tag, loop number, controller type) | Industrial, P&ID | Layered with feedback return | ST FB call and I/O entries |
| Cascade (levels 2–3), ratio (K), feedforward plus feedback, split range (outputs, ranges), selector/override (low, high or median; inputs) | Industrial, P&ID | Layered, nested inner loop | ST skeleton per loop |
| Interlock, permissive (conditions), cause-and-effect matrix (causes, effects) | Industrial, logic | Logic tree; matrix | ST Boolean logic per row |

Data-driven patterns, where a table generates the diagram, should sync both ways where the mapping is unambiguous, as Visio's Data Visualizer does with Excel ([Microsoft Support](https://support.microsoft.com/en-us/Visio/create-a-data-visualizer-diagram)). Examples are RACI to swimlanes, parent-id table to org chart and cause-and-effect table to matrix. The redundancy pattern deliberately serves two audiences: Douglass's TMR and the industrial 2oo3 share one topology. One generator should cover both.

## Resequence the cascades: model core before domain stencils

The current roadmap puts generic domain stencils (UML, BPMN, ER, network, org chart) in Cascade 4, with validation as a late add-on. **(synthesis)** Built that way, every one of those stencils would need rework once a model exists. Cascade 2 has already landed pages. Its remaining pieces matter mainly as substrate: containers carry statechart composites, swimlanes, zones and capability maps, and layers and arrange are prerequisites for patterns. Cascade 3, now being planned in another session, imports Mermaid and draw.io. Those importers should write model elements once the model exists, so Cascade 3's mapping layer should keep ids stable and stay thin. The revised plan below keeps both and reorders everything after them.

Two sequencing judgements deserve scrutiny. The first is putting the model core ahead of Cascade 3's completion. The alternative is to finish Cascade 3 first and retrofit importers later. That is viable only if Cascade 3's mapping layer stays a thin function from parser IR to commands, which is why the plan asks that session to keep ids stable rather than re-sequence its work. The second is choosing statecharts, C4 and ER as the first deep packs in their tracks. They have the most deterministic exports (SCXML, Structurizr DSL, DDL), mature open targets and existing parser support in `vizcraft-mermaid`. They therefore prove the codegen contract with the least domain risk. The P&ID pack carries the most standards risk, because ISA-5.1 and IEC 81346 detail is paywalled and the research could confirm only summaries. Its first release should lean on DEXPI's openly documented classes and on configurable tag formats rather than hardcoded letter tables.

## Conclusion

The research shifts the question from "which stencils should VizCraft add" to "what does a shape mean". In every audience studied, the valuable artefact is a typed, identified, validated model that several drawings, tables and generated files all reflect. The drawing is one projection of it. EPLAN's cross-references, AVEVA's open rule sets, itemis CREATE's `src-gen` folder and Structurizr's layout-loss problem are four views of the same lesson. VizCraft's command-per-action design with caller-chosen ids is the right foundation for that model. It is also a stronger agent story than the generation-centric MCP servers incumbents shipped in 2025. Agents that can query a pack's schema, apply validated edits, read back structured issues and regenerate code under a checked contract are doing engineering, not illustration.

The main uncertainties are external, not architectural. ArchiMate 4's final content, DEXPI 2.0's release status and the paywalled ISA and IEC detail all argue for packs as versioned data rather than code: a pack can be corrected when a standard is read without touching the engine. The other risk is scope. SysML v2 conformance, live cloud import and vendor-format interop (TIA Openness XML, Rockwell L5X) would each consume a cascade, and incumbents already serve them. The plan above deliberately stops at open formats and standard intermediates. There a small open-source tool can be best in class by being the visual front end to generators that already exist.
